# SMSForge — começar num host vazio

Esta é a entrada atual de instalação e continuidade de 24/10/2026. O handoff
de 21/10 permanece histórico; sua tag não contém o diagnóstico PB-13–PB-18,
o backlog de 55 itens ou este instalador.

## 1. Obter a revisão de continuidade

Instale Git e certificados HTTPS pelo gerenciador do sistema e clone:

```bash
git clone --branch codex/host-bootstrap-20261024 https://github.com/Misael-art/sms-forge.git
cd sms-forge
```

Depois da integração do PR, use a branch que contenha esse commit. Não voltar
à tag antiga para retomar o trabalho novo. Registre `git rev-parse HEAD`.

O alvo de validação do instalador é **Ubuntu 24.04 x86_64**, com Bash e Python
3.11–3.14. O launcher consegue instalar Python antes de chamar o wrapper.
Há receitas de pacotes para Debian e Arch/Manjaro, cuja instalação completa
precisa ser qualificada nesses hosts; não assumir paridade. Windows/macOS/ARM
exigem Linux x86_64 compatível, VM ou port explícito. WSL/containers podem
bloquear sandbox e áudio mesmo com todos os pacotes instalados.

## 2. Instalação

```bash
# Única elevação necessária: pacotes do SO. sudo pede a senha local se preciso.
bash tools/sms_wrapper/bootstrap_host.sh --apply --system-packages --profile full
source tools/sms_wrapper/host_env.sh
python tools/sms_wrapper/host_bootstrap.py --doctor --live-checks --profile full
```

Sem `--apply`, o launcher apenas relata pré-requisitos e não instala nada.
O Python do sistema não recebe pacotes pip. Os perfis são:

| Perfil | Conteúdo |
|---|---|
| `build` | SDCC, devkitSMS, makesms, venv/Pillow/NumPy/pytest e dependências |
| `qa` | build + JDK, Xvfb, bubblewrap, FFmpeg, PulseAudio e Emulicious fixado |
| `full` | qa + BlastEm fixado, instalado pelo wrapper de diagnóstico existente |

`ensure_toolchain.sh` permanece compatível e delega ao perfil build. Ele não
altera pacotes do SO sem `--system-packages`. Ativar `host_env.sh` em cada
shell mantém compilador, libs e ferramentas do checkout na frente do PATH.
Não editar `~/.bashrc`, não substituir Python/Java globais nem adotar um SDCC
do sistema apenas por ser mais novo. As bibliotecas foram compiladas com o
SDCC da cápsula e seu ABI é parte do pin.

O wrapper baixa os assets conhecidos da release `continuity-20261021` e
verifica **tamanho e SHA-256 antes de extrair**. Extrai somente SDK e
Emulicious, preserva a licença, rejeita traversal/links/arquivos especiais e
normaliza permissões. SDK/Emulicious existentes precisam coincidir; conteúdo
divergente é preservado e a instalação para com diagnóstico. Nenhum pin é
aprendido de um download divergente. O Python usa wheels com hashes em
`tools/sms_wrapper/requirements-host.lock`; OS/kernel/JVM seguem a distro e
são parte da requalificação de QA, sem promessa de reprodução de timings.

O smoke-test compila, linka e confere tamanho/header de uma ROM com SMSlib e
PSGlib. **Isso não executa a ROM.** Recibo por execução:
`out/host-bootstrap/runs/<id>/report.json`. Um retorno não zero exige ler
`problems`/`command_output`; pacotes presentes não equivalem a QA pronta.

### Sandbox e áudio

O doctor ativo exercita bubblewrap, consulta PulseAudio e compila a ponte
contra o JAR pinado. Em sessão gráfica Linux com PipeWire-Pulse, o servidor
existente pode atender ao protocolo Pulse. Em máquina sem sessão de áudio,
inicie um servidor PulseAudio do **usuário**, por exemplo `pulseaudio --start`,
e repita o doctor. Não iniciar um daemon global/root, trocar o sink padrão,
desabilitar políticas do kernel ou abrir o desktop para contornar uma falha.
Bubblewrap precisa de namespaces permitidos pelo host; reporte o bloqueio.

Depois do doctor, o agente segue os workflows centrais
`emulator-isolated-session.md` e `subagent-emulator-qa.md`. A aceitação real
da infraestrutura está em `session_bridge/acceptance.py --help` e
`session_bridge/audio_acceptance.py --help`: executar em sessão privada e
diretório exclusivo. Nenhum instalador garante controle isolado, música,
FPS ou jogo por conta própria. BlastEm complementa Z80/VDP/mapper; GDB M68K
não se converte em suporte de watchpoint Z80.

## 3. Restaurar o MUGEN sem herdar aprovações

O clone inclui `20261024-mugen-resume.tar.zst` e seu manifesto JSON neste
diretório: 3.917 arquivos, aproximadamente 81,9 MB expandidos/7,9 MB comprimidos.
O pacote preserva o `out/` recente do rev2 e a análise isolada de 24/10.
Não inclui SDK, senhas, configuração pessoal do usuário ou o `out/` legado de 3,3 GB.
Credenciais efêmeras Xauthority e caches regeneráveis são omitidos e listados
no manifesto; sessões de diagnóstico arquivadas não são sessões vivas completas.

```bash
source tools/sms_wrapper/host_env.sh
python tools/sms_wrapper/restore_handoff.py \
  --out out/handoff-20261024 --activate-build-inputs
python tools/sms_wrapper/build_inner.py --project SMS_projects/luta_mugem_rev2
```

O restaurador verifica hash do arquivo e **todos** os arquivos expandidos,
incluindo contagem/tamanho, em staging. O destino deve ser novo. Arquivos
restaurados ficam read-only; pedidos e sessões mantêm os caminhos antigos e
não são elegíveis automaticamente neste host. `--activate-build-inputs` copia
somente `out/generated` para o consumidor, se ainda não existe. Não ativa ROM,
evidência, projeção, `build_record`, ini pessoal ou caches de emulador.
Sem a opção, tudo permanece somente no diretório de consulta. Repetição em
destino existente é recusada; não apagar a origem para contornar o teste.

O build MUGEN pode resultar em SHA diferente da nominal histórica: identificar
fonte/dados/toolchain/data antes de atribuir causa. Não editar data/checksum
para fingir reprodução de payload ou transferir eixos do binário anterior.

Para OpenBOR, os recursos bancados e changelog já estão no Git:

```bash
python tools/sms_wrapper/build_inner.py --project SMS_projects/openbor_sms_rev1
```

O estado autoritativo continua no memory bank de cada consumidor. As releases
de 21/10 preservam acervo mais antigo, cuja restauração é opcional e separada.

## 4. Organização e consumo do host

- **Fontes/configuração/contratos:** Git, `tools/sms_wrapper/`, `doc/` e projeto
  canônico. `.agent` local existente não é sobrescrita. Um registry por projeto.
- **SDK/JAR:** `sdk/` e `tools/emuladores/emulicious/`. Só o wrapper administra
  os destinos que acabou de instalar. Customização divergente não é removida.
- **Instalação/cache:** `out/host-bootstrap/{venv,downloads,pip-cache,runs}`;
  staging temporário é removido em sucesso/falha. Uma instalação por checkout
  usa lock. Reservar ao menos 2 GiB livres, além do clone.
- **Medições:** saída nova por lote/SHA, sem reutilizar a última pasta. Anexe
  evidências necessárias ao registro canônico antes de descartar temporários.
  Use armazenamento Linux com permissões POSIX; não mover sessões vivas para
  cartão/shared mount que transforma tudo em 0777.
- **Processos:** sessões privadas com TTL e cleanup por ID; nunca matar Java,
  Xvfb, Pulse ou emuladores por nome global. No máximo três workers; FPS sob
  reserva cooperativa, sem medir performance concorrentemente. Jobs de build
  modestos e threads numéricas=1, já definidos no ambiente do wrapper.
- **Limpeza:** confira `du -sh out/host-bootstrap/*` e sessões próprias fechadas.
  Downloads/pip-cache podem ser descartados explicitamente com
  `python tools/sms_wrapper/host_bootstrap.py --prune-cache` quando não houver
  instalação ativa. Não remover venv/SDK/evidências/fontes como efeito colateral.
- **Agente/GitHub:** autenticação Git, Composio/Codex e credenciais são
  pessoais, não estão no pacote e não são necessárias para compilar. Configure
  seu agente com AGENTS.md e o prompt abaixo; não restaurar credenciais de outro
  host. RTK é ferramenta de shell do agente: usar quando disponível; os comandos
  de bootstrap acima podem ser executados com Bash/Python antes de instalá-lo.
